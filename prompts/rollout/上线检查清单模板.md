# 上线检查清单（模板）

改 Prompt、换模型或改参数，上线前照这张表逐项填。每一项都要有证据：链接到评测结果文件、PR 或标签记录。复制本文件，改名为 `checklist-<资产>-<版本>.md`。

## 1. 改了什么

| 项 | 填写 |
|---|---|
| Prompt 资产 | 例：`grounded-review/review-agent` |
| 新版本 / 现在线上的版本 | 例：`v1.3` / `v1.1` |
| 改动原因 | 发现了什么问题，证据在哪（失败案例编号、次数） |
| 改动内容 | 一两句话；链接到 diff |
| 影响范围 | 哪些请求会走到这个 Prompt；输出格式变没变（变了要升主版本号） |

## 2. 版本锁定

Prompt 和模型要一起锁定，否则回滚 Prompt 也未必能恢复原来的效果。

| 项 | 填写 |
|---|---|
| Prompt 文本指纹 | SHA-256 前 12 位 |
| 模型 | 写完整的模型编号，例：`claude-haiku-5-5`；不用会自动变的别名 |
| 参数 | effort、最大输出长度、温度、工具列表、输出格式定义的指纹 |
| 依赖的其他部件 | 例：evidence-check 核对脚本的版本、政策库的指纹 |

## 3. 回归测试（上线前必须过）

| 项 | 填写 |
|---|---|
| 评测集和版本 | 题数、答案什么时候定的、冻结文件和指纹 |
| 通过标准（跑之前写好） | 例：主指标不低于线上版本；护栏指标不变差；新问题的失败数降到 0 |
| 新旧分数 | 同一套题、同一个模型，两版并排；比例附 95% 区间和跑的次数 |
| 是否有退步 | 原来做对、现在做错的题逐条列出 |
| 结论 | 通过 / 不通过；不通过就不进入灰度 |

## 4. 灰度计划

| 项 | 填写 |
|---|---|
| 灰度比例 | 例：先 5–10% 的请求，按请求编号的哈希分流，同一个请求总是落在同一组 |
| 观察时长 | 例：24–48 小时，或者攒够 N 个请求（写明 N 怎么定） |
| 记录 | 每个请求记下用的是哪个版本（标签和指纹），否则事后分不清 |
| 放量节奏 | 例：10% → 50% → 100%，每一步都要过第 5 节的检查 |

## 5. 观察指标

| 指标 | 怎么算 | 线上版本的基线 | 方向 |
|---|---|---|---|
| 任务主指标 | 例：判对率、引文核对通过率 | 来自回归测试 | 越高越好 |
| 护栏：格式错误率 | 输出不合格式、字段填错位置的比例 | | 越低越好 |
| 护栏：误拒率 / 拒答率 | | | 越低越好 |
| 延迟 | 中位数和 95 分位 | | 越低越好 |
| 费用 | 每个请求的平均 token 和美元 | | 越低越好 |
| 人工复核量 | 进入复核队列的比例 | | 只作说明 |

## 6. 回滚条件（跑之前写好，触发就回滚，不再讨论）

| 条件 | 阈值 |
|---|---|
| 主指标比线上版本低 | 例：低于基线、且差距超过区间 |
| 任一护栏指标变差 | 例：格式错误率高于基线 1 个百分点 |
| 延迟或费用超标 | 例：中位延迟增加 30% 以上 |
| 出现新的严重错误 | 例：任何一次放过明确违规 |

**怎么回滚**：把 production 标签挪回上一个版本（`python scripts/prompts.py rollback <资产>`），记下原因；模型和参数按第 2 节一起恢复。
