# 上线检查清单示例：有据审核改稿建议 v1.3

照[模板](上线检查清单模板.md)填的示例。回归测试用的是项目里真实跑过的对比；灰度用评测题回放演示，**不是真实用户**。数字不在这里重抄，链接到生成的表。

## 1. 改了什么

| 项 | 填写 |
|---|---|
| Prompt 资产 | `grounded-review/advice` |
| 新版本 / 现在线上的版本 | `v1.3` / `v1.1` |
| 改动原因 | 存下的改稿回答里，模型有时把交答案的格式标签写进“回答”一栏，“修改后的文案”因此为空或只有一个词（[资产库 v1.2、v1.3 两行](../README.md#有据审核改稿建议)） |
| 改动内容 | 输出格式改成先填修改后的文案、再写说明；混进来的格式标签在代码里清掉，不多调用模型 |
| 影响范围 | 只影响“广告主追问怎么改”这一轮；审核本身的提示词不变；输出字段没有增减，只改了顺序 |

## 2. 版本锁定

| 项 | 填写 |

## 3. 回归测试

| 项 | 填写 |
|---|---|
| 评测集和版本 | mt4：改提示词之后新写的 12 条文字广告，跑前冻结；每版 3 遍 |
| 通过标准（跑之前写好） | 交上来的建议字段写错降到 0；品牌和价格保住不变差；费用不增加 |
| 新旧分数 | [资产库 v1.3 一行](../README.md#有据审核改稿建议)（字段写错、品牌价格、费用三项并排） |
| 是否有退步 | 没有：违规原话都去掉了、复审通过数和广告主自改版的判断都持平（项目评测报告 v1.3 一节） |
| 结论 | 通过 |

## 4. 灰度计划

| 项 | 填写 |
|---|---|
| 灰度比例 | 按“题号#第几遍”的哈希分流：10% → 50% → 100% |
| 观察时长 | 回放演示没有时间维度；真实上线时每一步至少观察 24 小时 |
| 记录 | 每个请求记下版本标签和指纹 |
| 放量节奏 | 每一步都过第 6 节的回滚条件才放下一步 |

## 5. 观察指标

| 指标 | 怎么算 | 方向 |
|---|---|---|
| 字段写错 | 交上来的建议里“修改后的文案”为空、只有一个词或混进格式标签 | 越低越好 |
| 品牌和价格保住 | 改后版本保留原广告的品牌名和价格 | 越高越好 |
| 每段对话费用 | 三轮对话的平均美元费用 | 越低越好 |

## 6. 回滚条件

- 灰度组的字段写错比例高于线上组；
- 灰度组丢品牌或价格的比例高于线上组；
- 灰度组每段对话的平均费用比线上组高 10% 以上。

## 7. 灰度结果（回放）

[canary-replay.md](canary-replay.md)：v1.3 每一步都没有触发回滚条件，放到全量。同一套规则下，v1.2 在 50% 那一步触发了“字段写错”和“费用”两条，回滚。
