# 统一评测协议

[English](eval-protocol.en.md)

这份协议把各项目已经在用的做法写成一份统一的说明。核心只有一句：**先写好答案和计划，冻结，再跑；每改一版就重测，分数变了、为什么采用都写清楚。**

评测分三层，按顺序做，前一层不过，后一层不做：

| 层 | 什么时候跑 | 回答什么问题 | 花不花钱 |
|---|---|---|---|
| 一、规则检查 | 每次改动都跑 | 输出的格式、引文、数字有没有坏 | 不花钱 |
| 二、模型评判 | 先校准，再在每个新版本上跑 | 规则查不了的质量：建议能不能直接用、判断有没有看错意思 | 少量 |
| 三、灰度对比 | 前两层都过了，最后才跑 | 新版本放给一部分请求后，指标有没有变差 | 看流量 |

---

## 〇、预注册：所有评测的共同前提

跑之前把下面五样写进项目的 `PREREGISTRATION.md`，并记下文件指纹（SHA-256 前 12 位）：

1. **题目和答案。** 答案在写题时定好，不在看到结果之后补。题目是在什么之后写的（例如“在第一轮结果出来之后写的”）照实写。
2. **打分脚本。** 打分规则写成代码，冻结；跑完以后改了打分，旧结果不再当作同一个评测报告。
3. **被测的东西。** 提示词、代码、模型编号、参数（effort、最大长度、工具列表、输出格式）。
4. **预期。** 每一组大概会得多少、哪一组更好；跑完逐条写“成立 / 不成立”。
5. **决定规则。** 跑之前写好“结果怎样就采用、怎样就不采用”，例如“新问题的失败数降到 0，且原来对的题不退步”。

跑完以后：

- 文件真的没变过：重新算指纹，和预注册里的一致。
- 跑之后改过的东西，写在预注册末尾的“跑后改动”一节，不改前面的内容。
- 没跑的写 **NOT RUN** 和原因，不写成“略”或空着。
- 已经冻结的结果不为了换发送方式（例如改用批量接口）重跑；和旧结果比较时写明发送方式变了。

各项目现在的做法：

| 项目 | 预注册文件 | 冻结了什么 |
|---|---|---|
| evidence-check | `eval/v2/PREREGISTRATION.md`、`eval/v3/`、`eval/v4/` | 题目、Skill 文本、核对脚本、打分脚本；Skill v0.2 在写留出题之前定稿 |
| 有据审核 | `eval/PREREGISTRATION.md`（留出集、v1.1、v1.2、v1.3、难题集、真实广告各一节） | 题目、提示词代码、打分脚本、图片；每一版改稿提示词都配一组新写的题 |
| 卖点体检 | `testset/*/PREREGISTRATION.md`、`testset/SUGGEST_PLAN.md`、`testset/ARM_A2_PLAN.md` | 题目、判断用的提示词、每一版修改建议的提示词 |
| 简历初筛 | `eval/PREREGISTRATION.md`，`eval/v2/` 到 `eval/verify/` 各一份 | 简历、答案、提示词；后几版用指纹检查，提示词一变就停 |
| 实时语音评测 | `eval/PREREGISTRATION.md`（主计划和十二份补充） | 题目、音频清单、打分脚本、每一项改进的设置 |
| AI 生图创作指南 | `data/freeze.json`、`data/实验/freeze.json` | 任务和评分表，生成之前冻结 |
| 有据标注流水线 | `docs/PREREGISTRATION.md`，第二到第四轮各一份，知识库问答和 Lark 工作流各一份计划 | 题目、提示词、采用标准、灰度回滚规则和预测；第四轮的采用标准和第三轮一字不改 |
| 有据经营分析 | `eval/PREREGISTRATION.md` | 题目、规则、提示词、模型和设置、打分脚本；跑前冻结文件指纹（`eval/frozen.json`），跑完核对都没变 |
| Cairn、TraceDesk | 没有预注册文件 | 题目和答案写好后才跑，但没有冻结指纹；这一点在评测卡的局限里写明 |

## 一、规则检查：每次都跑

规则检查是确定性的代码，不调用模型、不花钱，所以每次改动都跑，在 CI 里也跑。

**查什么：**

- **引文是不是原文。** 用 evidence-check 的脚本：引文必须逐字出自所引的文件，句子里的日期、时间、金额、数量也要出现在引文里。卖点体检里没通过的引文直接丢掉、不算证据；有据审核里没通过的引文在回答给出之前被拦下。
- **输出格式对不对。** 字段齐不齐、填没填错位置、有没有留下模板占位符。例如有据审核的改稿建议，就是规则检查发现“修改后的文案”字段有时写错位置，才有了 v1.2 和 v1.3。
- **打分脚本自己对不对。** 打分脚本带几条答案已知的样例，跑之前先过一遍自检（实时语音评测的 `score.py --check`）。
- **离线自检。** 每个项目的 `tests/`，不调用模型。

**规矩：**

- 规则检查失败，就不进入下一层。
- 规则只能查形式，不能查意思：一句真实的原文可能被拿来支持相反的说法。这部分交给第二层。

## 二、模型评判：先校准，再定期跑

有些质量规则查不了，例如“这条修改建议商家能不能直接照着改”“这个‘符合’是不是看错了简历”。这时用一个评分器：一个按评分表打分的模型调用，和被测的系统分开。

**先校准：**

1. 准备一组答案已知的样本：已知好坏的建议、植入的错误、写题时定好答案的题。
2. 用评分器打一遍，公布它和已知答案的一致率，写在评测卡的“评分器校准”一节。
3. 一致率不够，就改评分表，再校准，直到够了才拿去评被测的系统。参考目标是 90% 以上。

各项目的做法：

| 项目 | 评分器评什么 | 怎么校准 |
|---|---|---|
| 卖点体检 | 修改建议能不能直接照着改 | 先评已知好坏的建议；每条建议独立评两次，写两次之间的一致性 |
| 卖点体检 | 每条证据的第二次独立判断 | 先在答案已知的题上和答案对照 |
| 简历初筛 | 每个“符合”有没有看错 | 植入 40 条错读，再混入正确答案，看挑出多少、误报多少 |
| 有据审核 | 改后版本能不能通过 | 用单个提示词那一组复审；没有单独校准，这一点写进局限 |
| AI 生图 | 观感评分 | 独立评三次，算三次之间的一致性；没有和人工评分对照，写进局限 |

**定期跑：**

- 每个新版本都在新写、冻结的题上跑一遍，和上一版放在同一张表里。
- 评分表、评分器的模型或提示词一改，先重新校准，再用。
- 评分器和被测系统是同一个模型时，写进局限；条件允许就换一个不同厂家的模型当第二评分方。

## 三、灰度对比：最后才跑

前两层都过了，才把新版本放给一部分请求，看真实指标有没有变差。这些项目都没有线上流量，所以灰度只用评测题回放来演示，页面上写明“回放，不是真实用户”。

**做法：**

1. 版本和上线分开：`production` 标签指向线上版本，`staging` 指向候选版本。上线是把 production 挪到新版本，回滚是挪回去（`prompts/labels.json`、`scripts/prompts.py`）。
2. 按请求编号的哈希分流，同一个请求总落在同一组；每个请求记下用的是哪个版本。
3. 放量节奏写在上线检查清单里，例如 10% → 50% → 100%；每一步检查回滚条件。
4. 回滚条件在开始之前写好，触发就回滚，不再讨论。
5. 模型版本和提示词一起锁定，否则回滚提示词也未必能恢复原来的效果。

演示：[`prompts/rollout/canary-replay.md`](../prompts/rollout/canary-replay.md) 用有据审核的两次真实对比回放：v1.3 每一步都没触发回滚、放到全量；v1.2 在 50% 时字段写错和费用两条都触发，回滚。有据标注流水线按同样的做法跑了几轮回放：第一轮按事先写好的规则回滚，复盘发现规则本身写错；改好的规则在新写的广告上放到全量。它的第 3、4 版在采用标准这一关就没过，没有进灰度：假如照样放量，回滚规则也拦不下，所以采用标准和题目设计比灰度更早起作用。清单模板：[`prompts/rollout/上线检查清单模板.md`](../prompts/rollout/上线检查清单模板.md)。

## 四、怎么报告数字

1. **数字不手抄。** 评测卡和 Prompt 资产库里的数字都由脚本从项目的结果文件算出，并和项目记录逐条对照（`python scripts/build_cards.py --check`）。
2. **比例附 95% 区间，写明跑了几次。** 用 Wilson 区间；同一题跑两遍合并算的，写明“两遍不独立，区间偏窄”。
3. **先定义指标，再给数字；写方向和日期。** 每个指标写“越高越好 / 越低越好”，卡片写数据截至哪天。
4. **题目或评分规则改了，就是新的评测版本。** 单独一张表，不拿新旧分数相减。
5. **对比写全。** 新旧两版在同一套题上并排；“原来做对、现在做错”的题逐条列出。
6. **局限写成数字，每条配一条建议。**
7. **费用照实记。** 默认用最便宜的现行模型；几十次以上、不急着要结果的调用走批量接口（半价）；实时回路里的调用照旧用普通接口。

## 五、参考

- Hamel Husain，《Your AI Product Needs Evals》（2024）：评测分单元测试、人工和模型评测、A/B 测试三层。
- Aman Khan，《Beyond vibe checks》（2025）：评判先对照答案集校准，再用同一数据集和基线比。
- UK AISI，inspect_evals（MIT）：可能影响分数的改动要升版本、写前后分数。
- openai/evals（MIT）：用一组带标签的样本检验评分器本身。
- Hugging Face 模型卡模板（Apache-2.0）：评测卡的章节。
- Langfuse 提示词版本文档、promptfoo（MIT）：上线标签、回归评测和 CI。
